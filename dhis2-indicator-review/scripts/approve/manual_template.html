Two ways to open the page

Standalone file {{PREFIX}}-fix-review-standalone.html
No account needed. Open it in Chrome, Edge, Firefox or Safari; it works offline. Your decisions are kept in your browser, and you share them by sending a small decisions file (see “Working together”).
Claude link (artifact)
For people with a Claude account in the organisation. Decisions are saved for everyone automatically and appear live for the others. People who can only view the link can look but not approve.

Both show the same proposals and evidence and produce the same import files. This guide follows the standalone file; the Claude link works the same way, without the decisions files.

The page at a glance

  • Header: overall progress, Your name, Save decisions file, Load decisions files, and the four downloads.
  • Left rail: one entry per fix group. A group is one kind of change agreed in the review meeting, applied to every {{ITEM}} or {{AUX_SHORT}} that needs it. The bar under each entry shows approved (green) and rejected (red).
  • Overview and test evidence: how the fixes were tested (server syntax check, analytics before and after, comparison with an independent calculation, hand-written scenarios, screenshots).
  • Not proposed: agreed topics that still need a decision, with the reason for each.

Reviewing a group

The top of each group explains the change in one line and why it is needed. Where other systems use the same definitions (for example a report pipeline), a note says what the change means for them. If a scenario was tested on DHIS2 for the group, its expected and actual values before and after are shown. Below that is one card per {{ITEM}} or {{AUX_SHORT}}.

Reading a card

  • Chips under the name list every fix that touches this indicator and its state in each group.
  • Test data line: the indicator value on the test data before → after the fix, and whether DHIS2 matched an independent calculation.
  • Coloured notes: red = still fails after these fixes (with the reason); orange = the name and the definition don’t quite match; grey = other open topics on this indicator that are not changed here.
  • Show current vs proposed: side-by-side view of the changed fields ({{FIELDS}}). Removed parts are red and struck through, added parts are green. Tick Field names instead of UIDs to read field names.
  • Description: the proposed description is editable. Whatever is in the box is what gets exported.

{{AUX_SHORT_CAP}} cards show what changes in the {{AUX_SHORT}} and which {{ITEMS}} use it.

Approving and rejecting

  • Approve / Reject on a card records your decision for this fix on that item. Click the same button again to undo. Your name and the date appear under the buttons.
  • Approve all N pending at the top of a group approves every item you haven’t decided yet. Use it where the change is identical on every item (the header says “same change on every item”). Decisions you already made are left as they are.
  • Reset group clears every decision in the group.
  • Use Show: Pending and the search box to find what is left.
An item is exported only when every fix on it is approved. The proposed definition combines all its fixes. Approving one of them leaves the item “partly approved”, and it is not in the download yet. One rejection blocks the item.

The progress line in the header counts approved, partly approved, blocked and pending items separately.

Working together

With the standalone file, each person reviews in their own browser and sends their decisions to one coordinator, who merges them and produces the import files.

1. Share the fileThe coordinator sends {{PREFIX}}-fix-review-standalone.html to the reviewers (email, shared drive).
2. ReviewEach reviewer types their name, reviews their groups and approves or rejects.
3. Send decisionsEach reviewer clicks Save decisions file and sends the downloaded {{PREFIX}}-fix-decisions-<name>-<date>.json to the coordinator.
4. Merge and exportThe coordinator clicks Load decisions files, selects all received files, settles disagreements and downloads the import files.

Dividing the work

Reviewers don’t need to look at everything. Split the groups by programme area or by who knows the indicators best, and let one person review the {{AUX_SHORT}} groups. Anyone can still open any group. Items that sit in several groups are easiest when one person approves all their fixes.

Saving your progress

  • Decisions are kept in your browser automatically, so you can close the page and continue later on the same computer and browser.
  • They are not kept in a private/incognito window or after clearing browsing data. Save a decisions file now and then; you can load it back with Load decisions files.
  • A decisions file is small and contains only decisions, names, dates and edited descriptions. Send it, not the large HTML file.

How merging works

  • Decisions are merged per item and per fix. For each one the newest decision wins, whoever made it.
  • Loading the same file twice is harmless. You can load files at different times as they arrive.
  • Edited descriptions merge the same way: the newest edit wins.
  • A file saved from a different version of the page (for example after the proposals were updated) is still loaded, with a warning. Check those items again.

When reviewers disagree

The newest decision is kept, but disagreements are listed on the overview so they can be discussed. Once agreed, the coordinator sets the final decision on the card; as the newest decision, it is the one exported. To spread the outcome, the coordinator saves a decisions file and sends it back to everyone.

Using the Claude link instead

Everyone signed in with write access sees the same decisions live; there are no files to send. If two people change the same item, the last click wins. The downloads are identical.

Importing (for the DHIS2 administrator)

Import into a test copy first, run analytics and check a few indicators, then repeat on production. With curl, using your own server address and a personal access token with metadata write rights:

curl -H "Authorization: ApiToken $TOKEN" -H "Content-Type: application/json" \
  -X POST "https://<server>/api/metadata?importStrategy=UPDATE&atomicMode=ALL" \
  -d @{{ITEMS_STEM}}-approved-<date>.json

curl -H "Authorization: ApiToken $TOKEN" -H "Content-Type: {{AUX_CTYPE}}" \
  -X {{AUX_METHOD}} "https://<server>{{AUX_PATH}}" \
  -d @{{AUX_FILE}}

Check that the import report says "status": "OK" with the expected number of updated objects, then run the analytics tables update. The {{ITEM}} file can also be loaded with the Import/Export app (metadata import, strategy “Update”); {{AUX_IMPORT_NOTE}}.

Check for changes made since the export{{EXPORTED_NOTE}}. The files contain the complete {{ITEM}} objects and {{AUXS}} as they were exported, changed only where shown. If anyone has edited these {{ITEMS}} or {{AUXS}} since, importing would overwrite those edits. Compare first, or ask for the proposals to be regenerated from a fresh export.
